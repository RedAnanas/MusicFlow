# 双音乐库对账与补齐

本文档记录 MusicFlow 管理飞牛本地音乐库与 Apple Music 资料库的实施方案，并作为功能进度的唯一状态清单。每完成一个可验证功能，应同步更新状态和验收记录。

## 目标

- 通过 TuneMyMusic CSV 快照识别 Apple Music 资料库内容。
- 将 Apple Music 快照与 MusicFlow 已添加的本地音乐库进行对账。
- 通过 musicdl 搜索和下载缺失音乐，并按缺失情况补齐飞牛或 Apple Music。
- 所有下载和投递均由用户明确触发；低可信度匹配必须人工确认。

## 第一阶段设计

SQLite 数据库存放于运行时 `DATA_DIR/musicflow.db`，不提交到 Git。数据库保存不可由 JSON 配置可靠表达的快照、曲目和人工决策；原有设置继续使用 JSON。

CSV 必须包含以下列：`Track name`、`Artist name`、`Album`、`Playlist name`、`Type`、`ISRC`、`Apple - id`。文件通过浏览器上传，按内容 SHA-256 幂等导入，同一文件重复上传不会创建重复快照。

当前 TuneMyMusic 数据源按以下规则分类：

- `Apple - id` 以 `i.` 开头：用户上传曲目。
- `Apple - id` 为纯数字：Apple Music 目录曲目。
- 其他格式：未知类型，保留并等待人工判断。

匹配顺序：

1. 唯一且完全一致的 ISRC，自动匹配。
2. 唯一且标准化后的歌名、歌手、专辑一致，自动匹配。
3. 唯一且歌名、歌手一致但专辑不同，高可信自动匹配。
4. 歌名一致但歌手不同、多个候选、名称近似、繁简差异、别名或翻译名，全部列为待确认，不自动合并。

人工确认和否决结果持久化。新快照中不存在的历史曲目只标记为“可能已移除”，不直接删除。

## 第二阶段设计

musicdl 保持独立服务。MusicFlow 只通过内部 HTTP API 调用搜索、下载和文件读取接口，不复制 musicdl 源码，也不共享其 Cookie 或平台密钥到浏览器。

MusicFlow 保存下载任务和选择结果；musicdl 负责音源搜索、下载和基础标签写入。下载完成后，MusicFlow 将文件取回自身暂存区并校验文件大小、格式及校验值。

## 第三阶段设计

用户点击“补齐双库”后，根据对账状态执行：

| 当前状态 | 动作 |
| --- | --- |
| 双库都有 | 不操作 |
| 仅 Apple Music 有 | 通过 musicdl 下载到飞牛 |
| 仅飞牛有 | 将本地文件交接给 Apple Music |
| 两边都没有 | 下载一次，再分别写入飞牛和交接 Apple Music |
| 匹配不确定 | 人工确认后执行 |

任务分别记录飞牛和 Apple Music 两个目标的状态。部分失败时只重试失败目标，不重复下载。双库设置分别选择“仅含飞牛复制输出”和“仅含 Apple Music 交接输出”的两个独立监控目录；只缺一个库时仅投递对应目录，两边都缺失时下载一次并分别原子投递。Apple Music 自动导入目录由转换方案管理，交接文件必须先在监控目录外完成写入和校验，再原子移动到自动导入目录。“已接收”与“云端同步完成”保持为不同状态。

Apple Music 手工添加、公开曲库确认和自动交接会建立独立的增量记录，状态默认为“待快照确认”。这些记录立即参与发现音乐查重，但不会伪装成 CSV 已确认数据；后续导入新快照时按 Apple ID、ISRC 或标准化歌名、歌手、专辑自动升级为“快照已确认”。删除 CSV 快照不删除增量记录。Apple Music 公开网页搜索只用于展示曲库候选和打开 Apple Music 页面，不代表曲目已经加入个人资料库。

## 验收基准

- 样本 `My Apple Music Library (1).csv` 导入 1015 条，其中目录曲目 944 条、用户上传曲目 71 条、有 ISRC 910 条、无 ISRC 105 条。
- 重复导入相同 CSV 不产生新快照或重复曲目。
- Apple ID 重复但专辑或语言不同的记录不会被破坏性合并。
- 人工确认结果在服务重启后仍存在。
- 页面明确显示快照时间和过期提示。
- 自动匹配必须给出匹配依据；不确定匹配不会自动下载或交接。
- 最终目录中不出现未完成文件；一键补齐只执行缺失目标。
