# 上传签名离线性能验证

2026-10-16，使用“还是会想你 - TieZ”转换成品的前 10 秒，统一转换为 16 kHz 单声道 float32 PCM。测试不读取授权、不请求 Apple，也不重新上传已成功歌曲。

| 环境 | 原指令计数 | 关闭指令计数 | 耗时降低 |
| --- | ---: | ---: | ---: |
| Windows 开发环境 | 10.468 秒 | 7.548 秒 | 27.9% |
| 本地 Linux Docker | 10.293 秒 | 8.744 秒 | 15.1% |
| 飞牛 i5-7200U Docker | 24.556 秒 | 20.590 秒 | 16.2% |

三种环境、两种执行方式的签名 SHA-256 均为 `9c672a355e68592600d632e49efc703d52efb9262d02f32f7e2db7394d69ac83`。这是单次短片段对照，不代表整首歌或所有歌曲都能获得相同比例的收益。NAS 的算法挂载只读，测试容器不挂载生产授权或数据库，完成后删除测试容器。

本地 Linux Docker 对同一首歌截取的约 10 秒 AAC 成品进行缓存测试：首次生成 6.672 秒，重新实例化上传器后的缓存命中 0.036 秒，包含 FFmpeg 解码校验，签名字节一致。该测试只覆盖签名步骤，不代表完整上传耗时。

主要修改：音频签名仿真取消逐指令计数，保留每次调用 30 秒超时与返回点检查。SAP 握手、请求签名及旧版 partial/full-lowres 指纹的指令上限不变。持久缓存另按实际解码的 PCM、算法和 PCM 规则区分，完整性不符时重新计算；缓存命中仍保留解码校验，跳过仿真，避免容器裁剪信息不同导致误命中。

复现方式：

```text
ffmpeg -nostdin -hide_banner -loglevel error -i song.m4a -t 10 -ac 1 -ar 16000 -f f32le sample.pcm
python scripts/benchmark-upload-signature.py --pcm sample.pcm --binary /private/algorithms/AMPLibraryAgent.exe
```

第二条命令需要现有 Unicorn、pefile 及相邻的匹配版本 CoreFP.dll。测试分别运行旧计数方式和当前方式，签名不一致时直接报错。容器内可用 `--runtime /app/upload-runtime` 指定运行时目录。算法二进制和歌曲样本不进入仓库。

首次上传仍计算整首签名，不使用截取片段替代正式签名。是否触发该算法取决于当前工作响应，界面显示签名百分比和本次耗时，不预测剩余时间。

## NAS 长等待会话对照

同日对一首歌曲的 NAS 未完成会话与本机 Linux Docker 成功会话作只读比较。两端 M4A SHA-256 一致，授权包创建时间、认证头、上传配置、资料库上下文、公共协议字段及上传代码均一致。单曲元数据仅有文件名、创建/修改日期、随机 persistent-id 与 match-id 不同。比较中授权与上下文只计算临时 HMAC，不输出原值。

- NAS：首次 `downloadRequests` 即返回 HTTP 200、status=0、retry-in-ms=180000；此后持续无动作，30 分钟后执行器按期限结束。恢复原会话后仍等待。没有上传音频，也未进入签名计算。
- 本机 Docker：首次查询即取得 hash-track，随后取得 partial、signature、音频准备、上传和 complete。签名 54.3 秒，总耗时约 101.5 秒，完成协议及资产确认；跨设备播放仍需用户核对。
- NAS 上一首成功任务使用同样的非 `-2` 上传入口，随机 match-id 同样为 63 位。因此入口域名差异或编号位数不是已证实的故障原因。
- 两台宿主默认网关相同，但部分 Apple 域名的当前 DNS 解析存在差异，不能据此证明或排除完整网络路径的影响。通用公网出口探测在 NAS 未成功，不能声称已确认出口一致或不同。

失败会话的响应不含占用者、过期原因或明确拒绝说明。官方客户端在 NAS 任务建立时运行，关闭后旧任务仍等待；本机成功任务在关闭客户端后新建。会话竞争是候选解释，尚不能视为根因。12→13 的状态转换已有官方采样及既有回归依据，不能为了试错擅改协议状态。

按用户要求停止 NAS 指定任务，保留原加密记录并备份任务数据库，再以同一 M4A 在本机新建一次获准的对照上传。原 NAS 任务保持 cancelled，本机为 cloud_completed，未重试其他歌曲。下一步需在官方客户端关闭、无并发上传时，使用另一首未上传歌曲建立新的 NAS 会话；在取得新证据前不修改授权、DNS、代理或上传协议，不自动重建原曲目。

### 新歌曲与原会话移交对照

用户在 NAS 提交“先说谎的人”，官方客户端和后台代理均已退出，本机无活动上传。NAS 新任务首次工作查询仍为 status=0、retry-in-ms=180000、无工作指令。因此仅凭关闭客户端或换一首歌，并未解除现象，不能将客户端竞争认定为根因。

用户随后明确批准将这个原会话移交本机 Linux Docker。停止 NAS 当前任务前确认无其他活动任务，备份 SQLite 后只将该任务标记 cancelled，再恢复 NAS 服务。复制停止后的最新加密记录和相同 M4A，在本机校验现有密钥可解密且账号与资料库上下文匹配；通过既有恢复入口接续原会话，未重新提交单曲元数据。开始恢复后确认云端条目相同、元数据提交次数仍为 1。恢复入口先重放最后的明确响应并遵守其 180 秒退避，不能把这段本地等待误报为新云端响应。最终结果需以实际新请求及工作指令为准。

移交后的新请求仍返回 180 秒等待。随后对原 `update-id` 查询更新状态，确认 `session-id` 未变，但四个工作路由已更新。暂停执行器并备份原加密记录后，使用新路由查询同一条目，立即取得 `hash-track`；恢复执行器后收到音频及附加资产完成确认，状态为 `cloud_completed`，签名耗时 32.1 秒，元数据提交次数始终为 1。跨设备播放尚需人工核对。

该对照证明刷新路由后原会话能够推进，不足以断言 Apple 内部的全部原因。当前实现对至少 180 秒的空闲退避，在完整等待后查询原更新的工作路由，只接受相同会话编号，持久化新路由并保留原曲目和工作序号。短等待及待提交票据不增加查询；会话编号变化则停止并保留记录，不自动新建条目。

修复后后端 172 项测试通过；上传器 Windows 与 Linux 各运行 101 项测试，分别跳过 6 项和 3 项平台相关测试，其余通过。编译、前端构建、Compose 配置和差异空白检查通过。本机与 NAS 已部署同一测试镜像，两端页面及健康检查返回 200、执行器在线。NAS 原移交任务保持停止。

随后 NAS 独立上传“冬眠·2023 (DJ阿布版)”：依次处理 partial、full-lowres 指纹和音频签名，最终状态为 `cloud_completed`。从入队到完成约 445.2 秒（7 分 25 秒），音频签名 172.6 秒；其余步骤没有完整的逐阶段计时，不能将差值全部归为 full-lowres 计算。该任务持续推进，未观察到三分钟空闲退避，因此证明 NAS 完整流程可用，但不单独证明自动路由刷新分支已在 NAS 触发。用户随后确认跨设备播放验证通过。
